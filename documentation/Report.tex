    \section{Introduction}
    \label{Introduction}
    
    Chess is a centuries old board game that has adapted well to the internet age. \textit{Chess.com}, the largest online chess platform, has over ten million games played on it every day \citep{chessdotcom-about}. 
    
    The online nature of these platforms enable features that don't exist when playing chess with a physical board and pieces. \textit{Lichess.org} introduced voice recognition to make moves in 2023 \citep{lichess-voice}, and \textit{Chess.com} offers alternative animations when moving or capturing pieces. However, there is little published evidence on whether such features improve user enjoyment.
    
    The goal of our project is two-fold. Firstly, to create a website for playing chess that implements three features: 
    \begin{itemize}[noitemsep]
    	\item Computer opponents that have human-like move times.
    	\item Alternative move and capture animations
    	\item Voice-command move input
    \end{itemize}
    Secondly, to investigate whether these features affect user enjoyment through surveying and conversational user evaluation sessions.

    \section{Project architecture}
    \label{Project architecture}

    \subsection{Why design and build a microservices architecture?}
    \label{subsec:why-microservices}

    When designing Checkmate+, we chose a microservices architecture over a monolith. Several factors affected this decision. First, live chess matches are stateful: they are held in the memory of the Game Server for the duration of the match. This is different from a stateless service like authentication, where any pod can serve any request because no per-request state lives on the pod. Second, the post-game analysis engine wraps a native Stockfish binary, which was simpler to isolate in its own service than to embed inside an HTTP-serving Spring Boot process. Third, splitting the system into smaller deployable components lets us redeploy a single service after a bug fix without redeploying the whole platform, and contains the blast radius of a crash to a single pod. Kubernetes restarts the failed pod while the rest of the system is unaffected.

    This approach comes with its costs. Every call inside the cluster is a point of failure with its own network semantics, intra-cluster networking must be considered, \texttt{.proto} contracts must be kept in sync across services, and the deployment topology is much more complex than a single monolith. Given that the project aims to build a chess platform comparable in operational shape to Chess.com or Lichess, we judged these costs acceptable and chose to build with scale in mind using the tools enterprises use to run systems of this kind.

    \subsection{Overview}

    \begin{figure}[H]
        \centering
        \includegraphics[width=0.9\textwidth]{diagrams/00-overview}
        \caption{High-level overview of the Checkmate+ platform.}
        \label{fig:overview}
    \end{figure}

    \begin{enumerate}
        \item \textbf{The Game Server (GS).} Responsible for holding live game states; players are connected to a Game Server pod for the duration of a match.
        \item \textbf{The Game Server Manager (GSM).} Responsible for keeping track of active matches and balancing match allocation across Game Server pods. Tracks match lifecycle in Redis.
        \item \textbf{The Matchmaking Service (MS).} Responsible for player requests to join matchmaking. Asks the GSM for a free server and tells the client where to connect over STOMP.
        \item \textbf{The Player Service (PS).} Responsible for the main user-facing API, owns authentication and the database storing player data. Issues JWTs that every other backend service validates.
        \item \textbf{The Stockfish Engine (SE).} Responsible for analysing completed matches using the Stockfish chess engine and returning per-move evaluations to the Player Service.
        \item \textbf{The Voice Command Service (VC).} Responsible for the voice command feature, letting users use their voice to make moves.
        \item \textbf{The Chess Library.} Not a service, but a shared Kotlin library used across the backend. Contains the shared types, the chess engine implementation, and the human-like move time model.
    \end{enumerate}

    \subsection{Inter-service communication}
    \label{subsec:inter-service-communication}

    Checkmate+ uses four different communication mechanisms.
    Each was chosen based on the requirements of the interaction it serves, rather than for consistency across the system.
    The frontend talks to the backend over three protocols (Figure \ref{fig:frontend-transports}), and the backend services talk among themselves using gRPC (Figure~\ref{fig:service-topology}).

    \begin{figure}[H]
        \centering
        \includegraphics[width=0.9\textwidth]{diagrams/02-frontend-transports}
        \caption{Protocols used between the frontend and the backend services.}
        \label{fig:frontend-transports}
    \end{figure}

    Between the browser and the backend, the choice of protocol follows the shape of the data being exchanged.
    Requests against the Player Service use GraphQL, served by Spring's GraphQL starter, because the frontend often needs slightly different shapes of player profile or match history data on different pages, and a single GraphQL endpoint lets the client pick the fields it needs without the backend exposing a new REST route every time.
    The Matchmaking Service and the live Game Server both use STOMP over SockJS rather than plain WebSocket, because each interaction is bidirectional and pub/sub in nature: the client subscribes to a ``match found'' topic on the Matchmaking Service while it waits in the queue, and subscribes to a per-match topic on the Game Server during a live game so that the opponent's moves can be pushed without the client polling. STOMP gives us a frame format and subscription model on top of the raw WebSocket transport. Finally, the Voice Command Service exposes a plain HTTP POST endpoint, because voice input is a one-shot request-response with no need for a persistent connection.

    \begin{figure}[H]
        \centering
        \includegraphics[width=\textwidth]{diagrams/01-service-topology}
        \caption{Service topology of the Checkmate+ backend, showing gRPC links between services and dependencies on PostgreSQL, Redis, and the OpenAI API.}
        \label{fig:service-topology}
    \end{figure}

    Backend services communicate with each other over gRPC. The Matchmaking Service asks the Game Server Manager for a free Game Server, every Game Server sends a heartbeat to the Game Server Manager every 30 seconds, the Game Server reports completed matches to the Player Service, and the Player Service sends matches to the Stockfish Engine for analysis.
    gRPC was chosen for these calls because the contracts are stable and well-defined, and gRPC's protocol buffer schemas make the contract explicit and the wire format compact compared to JSON over HTTP.

    One cost of this approach is that the gRPC contracts live as duplicated \texttt{.proto} files inside each service that needs them, rather than as a single shared module.
    A change to a service's gRPC API therefore requires updating every other service that consumes it, and a missed update will compile cleanly but fail at runtime with a message mismatch.

    All backend services run on the JVM as Spring Boot applications written in Kotlin, which gives us a single tooling story across services even though each is a separate deployable.

    \subsection{Authentication}
    \label{subsec:authentication}

    All authenticated calls between the frontend and the backend, and between the backend services themselves, are authorised using a JSON Web Token (JWT). Figure~\ref{fig:auth-hmac} shows the arrangement.
    The Player Service issues a JWT after a successful user login (the login flow itself is covered in Section \ref{Front-end}). Every other backend service runs Spring Security as an OAuth2 resource server and validates that token on each incoming request. The token is supplied as a bearer header on HTTP and GraphQL requests, and on the initial \texttt{CONNECT} frame of STOMP sessions.

    \begin{figure}[H]
        \centering
        \includegraphics[width=0.8\textwidth]{diagrams/04-auth-hmac}
        \caption{The Player Service issues JWTs; every other backend service validates them using a shared HMAC secret.}
        \label{fig:auth-hmac}
    \end{figure}

    The tokens are signed with HMAC-SHA256 using a symmetric secret (\texttt{jwt.secret}) that is shared across all backend services as an environment variable.
    This is simpler than running a separate identity provider and avoids an additional service in the dependency graph, at the cost of two trade-offs.
    First, every service must be deployed with the same secret value; a mismatch will silently 401 every cross-service call.
    Second, the secret cannot be rotated without redeploying all services together, so a leak of the secret would require coordinated remediation across the system.
    These drawbacks were judged to be acceptable for the scale of the project.
    In a production deployment at higher scale would likely benefit from an asymmetric signing scheme (RS256) where only the issuer holds the signing key.

    \subsection{Match lifecycle: a worked example}
    \label{subsec:match-lifecycle}

    To highlight the role of each service, this section traces a single ranked match from the user pressing ``Find game'' to the post-game analysis being available.
    Figure~\ref{fig:match-lifecycle} shows the sequence.

    \begin{figure}[H]
        \centering
        \includegraphics[width=\textwidth]{diagrams/03-match-lifecycle}
        \caption{Sequence of interactions during a ranked match, from queue entry to analysis being available.}
        \label{fig:match-lifecycle}
    \end{figure}

    When the user clicks ``Find game'', the frontend opens a STOMP connection to the Matchmaking Service and joins the queue.
    The Matchmaking Service asks the Game Server Manager, over gRPC, for a Game Server with capacity.
    The Game Server Manager replies with the endpoint of an allocated Game Server pod, and the Matchmaking Service publishes a ``match found'' message to the user's STOMP topic containing the WebSocket URL and a match identifier.

    The frontend then opens a second STOMP connection, this time to the allocated Game Server, presenting the user's JWT on the \texttt{CONNECT} frame.
    From this point on, all moves are pushed by the client into the Game Server and the resulting board state is broadcast to both players over their subscribed topic.
    The Game Server holds the authoritative game state in memory for the duration of the match.

    When the match ends, the Game Server submits the completed match to the Player Service over gRPC. The Player Service persists the match to PostgreSQL and enqueues an analysis job for the Stockfish Engine through Redis on player request.
    The Stockfish Engine consumes the job, analyses each move, and returns the evaluations back to the Player Service.
    Some time later, when the user opens the match in their history, the frontend fetches the analysis with a GraphQL query against the Player Service.

    This single example utilises all four communication mechanisms described in Section~\ref{subsec:inter-service-communication} and every backend service in the platform.

    \subsection{Deployment}
    \label{subsec:deployment}

    Checkmate+ is deployed to a Kubernetes cluster as a single Helm chart, with everything described above running in one namespace.
    The deployment is split across two figures: Figure~\ref{fig:deployment-ingress} shows how public traffic enters the cluster and the services it reaches, and Figure~\ref{fig:deployment-data} shows the internal services and stateful subcharts together with the gRPC links between them.

    \begin{figure}[H]
        \centering
        \includegraphics[width=\textwidth]{diagrams/05a-ingress}
        \caption{Ingress path and publicly reachable services. Public traffic enters via Cloudflare and is forwarded through the in-cluster \texttt{cloudflared} agent to a per-service ClusterIP, which in turn fronts one or more pods.}
        \label{fig:deployment-ingress}
    \end{figure}

    \textbf{Ingress via Cloudflare Tunnel.} Rather than using a traditional Kubernetes ingress controller with a public load balancer, the cluster runs a single \texttt{cloudflared} agent pod which opens an outbound tunnel to the Cloudflare edge.
    Public traffic for Checkmate+ enters Cloudflare's edge and is routed back through that tunnel to a ClusterIP Service inside the cluster.
    This avoids exposing any inbound ports on the cluster's host and offloads TLS termination, DDoS protection, and DNS to Cloudflare.
    The routing rules (six public hostnames such as \texttt{checkmateplus.org} for the frontend, \texttt{playerservice.checkmateplus.org} for the GraphQL API, and \texttt{gs0.checkmateplus.org} / \texttt{gs1.checkmateplus.org} for the individual Game Server pods) are configured in the Cloudflare Zero Trust dashboard rather than in the Helm values, which simplifies route changes but means the dashboard controls what is publicly available.

    \textbf{StatefulSet for the Game Server.} The Game Server is deployed as a Kubernetes StatefulSet rather than a Deployment, fronted by a headless Service.
    This gives each Game Server pod a stable per-pod DNS name (\texttt{gameserver-0.checkmateplus-gameserver}, \texttt{gameserver-1.checkmateplus-gameserver}, and so on), which is required for the Game Server Manager to route a specific match to a specific pod.
    A regular Deployment with a round-robin Service would send the player to whichever Game Server pod the load balancer picked, which would not necessarily be the pod holding the game state for their match.

    \begin{figure}[H]
        \centering
        \includegraphics[width=\textwidth]{diagrams/05b-data}
        \caption{Internal services and stateful subcharts. The Game Server Manager and the Stockfish Engine are not exposed publicly; PostgreSQL and Redis are deployed via Bitnami's Helm subcharts inside the same release.}
        \label{fig:deployment-data}
    \end{figure}

    \textbf{Stateful dependencies.} PostgreSQL and Redis are deployed via Bitnami's Helm subcharts inside the same chart.
    PostgreSQL holds the player and match data and is managed by Flyway migrations shipped inside the Player Service.
    Redis carries session data and the post-game analysis queue between the Player Service and the Stockfish Engine.

    \textbf{Container images.} Production images are built using Spring Boot's \texttt{bootBuildImage} task with the Paketo Buildpacks, producing GraalVM native images compiled with \texttt{-O3} and tuned with G1 GC. Native images give significantly faster startup and lower memory footprint than equivalent JVM images, which matters when running multiple Spring Boot services in one cluster.
    Two services, the Player Service and the Voice Command Service, currently ship as JVM images instead of native ones due to a regression in their native builds that has not yet been resolved; this is reflected in their image tags (e.g.\ \texttt{2.2.2-jvm}) and in the resource requests in the Helm values.

    \textbf{GitOps with Flux CD.} The Helm release itself is reconciled into the cluster by Flux CD, which watches the project's Git repository and applies any changes to the chart or values file automatically. Secrets, including the shared \texttt{jwt.secret} discussed in Section~\ref{subsec:authentication}, are stored as Sealed Secrets in the same repository, encrypted to the cluster's public key so that they can be checked in safely.


    \section{The computer opponent}
    \label{The computer opponent}
    
    Online chess platforms often offer the option to play against a computer opponent (also called a ``bot''). The moves that a bot makes is determined by a program called a ``chess engine''. For \textit{Checkmate+}, we created our own chess engine, covered in section \ref{Chess engine}.
    
    Another aspect to the experience of playing against a bot is how long they take to make their moves. For \textit{Checkmate+}, we implement a feature that neither \textit{Chess.com} or \textit{Lichess.org} have: bots that have human-like move times. This feature will be covered in section \ref{Human-like move time model}.

    \subsection{Chess engine}
    \label{Chess engine}

    \subsubsection{Background Research}
    Before implementing the engine, we carried out background research into common chess engine designs. Most engines are built around four main components: \citep{cpwiki-getting-started}

    \begin{itemize}
        \item A board representation to store the current position.
        \item A move generator to produce possible moves.
        \item An evaluation function to score positions.
        \item A search algorithm to choose the best move.
    \end{itemize}

    We also looked at the difference between pseudo-legal and fully legal move generation, as well as the use of move ordering to improve search efficiency. This research helped us to decide on a square-based board representation and a traditional minimax search with alpha-beta pruning, which were both suitable for a project of this scale.

    \subsubsection{Move Generation}
    Move generation is the process of producing all possible moves from a given board position, and forms the foundation of the search algorithm \citep{vrzina-chess-engine}. We implemented two stages of move generation.

    The first stage, implemented in \texttt{generateAllMoves()}, produces pseudo-legal moves for all pieces belonging to the side to move (black/white). This generates candidate moves for each piece type - pawns, knights, bishops, rooks, queens and kings - based purely on their movement rules, without checking whether the resulting position leaves the moving side's king in check. Each piece type has its own generation function, making the rules for each piece clear and easy to maintain independently.

    The second stage, implemented in \texttt{generateLegalMoves()}, filters these pseudo-legal moves to produce only fully legal moves. Each candidate move is applied to a copy of the board, and any move that left the moving side's king in check is discarded using the \texttt{isInCheck()} function. This ensures that the search algorithm only considers legal positions. Special rules including castling, en passant, and pawn promotion are all handled explicitly within the individual piece generation functions.


    \subsubsection{Search Algorithm}
    The search algorithm is responsible for choosing the best move from a given position by looking ahead at possible future game states. We implemented a minimax algorithm with alpha-beta pruning, which is the standard approach for classical chess engines \citep{cpwiki-minimax}.

    Minimax works by modelling the game as a tree of positions. White aims to maximise the evaluation score while black aims to minimise it. At each node, the algorithm applies a move to produce a new board state and recursively evaluates the resulting position. When the search reaches its maximum depth, the position is scored using the evaluation function. The best move is then the one that leads to the highest score for white, or the lowest score for black.

    To improve efficiency, we implemented alpha-beta pruning. This technique maintains two values - alpha, the best score white can guarantee, and beta, the best score black can guarantee. If a move is found that is worse than the current best for the side to move, that branch is cut off and not explored further. This significantly reduces the number of positions the engine needs to evaluate without affecting the result.

    We also implemented iterative deepening, where the engine performs searches at increasing depths before reaching the target depth. Counter-intuitively, this improves overall performance because earlier searches populate the transposition table - a cache of previously evaluated positions - which helps prune the deeper search more effectively. Move ordering is applied at each node using the transposition table's best move and captures of valuable pieces, further improving the efficiency of alpha-beta pruning.

    \subsubsection{Evaluation Function}
    The evaluation function scores a board position from White's perspective, returning a positive value if White is better and a negative if Black is better. This score is used by the search algorithm at the leaves of the search tree to determine which positions are favourable.

    The foundation of the evaluation is material balance. Each piece type is assigned a fixed centipawn value: pawns are worth 100, knights 315, bishops 330, rooks 500, queens 900 and kings 20000. The total material score is computed by summing White's piece values and subtracting Black's. This alone produces a functional engine that avoids losing material unnecessarily.

    Beyond material, the evaluation includes several positional heuristics to encourage stronger play. Piece-square tables are applied to pawns and knights, assigning a bonus or penalty based on the square a piece occupies. Pawns are rewarded for advancing toward promotion and for occupying central squares, while knights are penalised for sitting on the edges of the board where their mobility is reduced. Rooks receive a bonus for being placed on open or semi-open files, where no pawns obstruct their activity, as well as an additional bonus for reaching the seventh rank, where they can threaten the opponent's back rank. Passed pawns - those with no opposing pawns blocking or guarding their path to promotion - are given a bonus that scales with how far they have advanced.

    \begin{figure}[H]
        \centering
        \includegraphics[width=\textwidth]{diagrams/06-evaluation}
        \caption{Example evaluation of a board position, showing material balance
        and positional bonuses contributing to the final score.}
        \label{fig:evaluation-function}
    \end{figure}

    Together, these heuristics produce an engine that plays more purposefully than one relying on material counting alone, guiding the search towards positions with better piece activity and long-term structure.

    \subsubsection{Tuning and Testing}
    Testing was carried out using a comprehensive suite of unit tests written in Kotlin using the standard \texttt{kotlin.test} framework. These tests cover all major components of the engine, from low level board utilities to high-level search behaviour, ensuring correctness at every layer.

    Board correctness was verified through several categories of tests.
    \begin{itemize}
        \item Coordinate conversion functions such as \texttt{toFileRank()}, \texttt{toSquare()}, and \texttt{toAlgebraic()} were tested against known square indices.
        \item Move application was validated for standard moves, captures, castling in all four directions, en passant and promotion to all four piece types.
        \item The half-move clock and full-move counter were also tested to confirm they increment and reset correctly under pawn moves, captures, and piece moves.
    \end{itemize}

    Legal move generation was validated using Perft, a well-established engine testing technique that recursively counts the total number of positions reachable from a given position at a fixed depth and compares this against a known correct value. We used the ``kiwipete`` position, a standard benchmark position specifically designed to exercise edge cases in move generation such as en passant, castling, and promotion. In practice, this provided a reliable way to confirm that the move generator behaved correctly at depth 5.

    The evaluation function was tested by constructing positions with known material imbalances and asserting the correct sign of the score. Cases tested include an extra pawn, a rook-for-minor-piece exchange, a queen versus rook and minor piece and a minor piece versus two pawns.

    Search quality was verified by testing the engine on a range of tactical and strategic puzzles at various depths. These included back-rank mates in two, material wins in one and two moves, a mate-in-three sequence, stalemate avoidance, passed pawn advancement, rook placement on open files and kingside and queenside castling to complete development. The engine was also tested for correct underpromotion, choosing a knight over a queen in a position where promoting to a queen would result in a stalemate.

    \subsection{Human-like move time model}
    \label{Human-like move time model}
    
    The time a computer opponent takes to reply to a user's moves affects the user experience. While it's usually best to minimise delays or loading times in software applications, a bot that replies near-instantly isn't ideal.
    
    \begin{quotation}
    	Paradoxically enough, moving as quickly as possible is not necessarily desirable. Users tend to get frustrated once they realize how little time their Mac really spends to crush them at low levels. In the interest of promoting harmonious Human - Machine relations, we enforce minimum response times \citep{apple-chess-engine}.
    \end{quotation}
    
    When creating Mac OS X's Chess application, the developers at Apple added a minimum delay of two seconds before the computer play its moves to avoid frustrating users. A more nuanced approach could improve on this. Human players do not take a uniform two seconds per move: some moves are obvious and are played quickly, while others warrant a longer think. A move time model that reflects this would feel more natural to play against. It could also increase user enjoyment, as a bot taking noticeably longer to reply may give the user the feeling that they have posed a genuine challenge, even if the bot is not truly ``stumped''.
    
    \subsubsection{Data}
    
    To train such a model, we used game data from the Lichess.org open database
    \citep{lichess-db-univ}. We used the January 2019 dataset, which contains millions of games along with each player's clock times in centisecond precision.
    
    The first 100,000 games in the dataset were filtered to only include those where a clock annotation exists for every move, and where at least four moves were played. Abandoned games and non-standard variants were excluded, as were casual (unrated) games on the basis that they're taken less seriously and may introduce noise. 55.72\% of games made it through this filtering.
    
    Moves in each game were converted into rows in our dataset for training the model. Each row contains the following features:
    
    \begin{itemize}[noitemsep]
    	\item \texttt{initial\_time}, the number of seconds on the clock when first starting the game. This feature is the same for all moves within the same game.
    	\item \texttt{increment}, the number of seconds added to each player's clock after they make a move. Like \texttt{initial\_time}, this feature remains the same for all positions within the same game.
    	\item \texttt{time\_remaining\_for\_this\_position}, the time in seconds remaining on the player's clock for them to make their move.
    	\item \texttt{time\_opponent\_took}, the time in seconds the opponent spent on their previous move.
    	\item \texttt{number\_of\_legal\_moves}, the number of legal moves available to the player in the current position.
    	\item \texttt{in\_check}, whether the player's king is currently in check.
    	\item \texttt{was\_capture}, whether the move just played by the opponent was a capture.
    	\item \texttt{move\_number}, the full move number of the current position. This number increases as a game progresses.
    	\item \texttt{time\_taken\_for\_this\_position}, the target feature. How many seconds the player took to make their move.
    \end{itemize}
    
    Note that since players' clocks don't tick down for their first move on \textit{Lichess.org}, the first 2 moves of every game aren't converted into rows in our training dataset so that we don't have any null values.
    
    In the end, our dataset for training move time models has 3,481,887 rows. This work can be seen in \texttt{/EngineMoveTimeModel/src/main/python/PGN to CSV.ipynb}.
    
    For training the linear regression model, two engineered features were included to help model non-linearity in existing features:
    
    \begin{itemize}
    	\item \texttt{time\_pressure}, defined as $\frac{1}{1 + t}$ where $t$ is \texttt{time\_remaining\_for\_this\_position}, grows sharply as a player's clock runs low. The idea being that players play faster when low on time to avoid losing via timing-out.
    	\item \texttt{opening\_unfamiliarity}, defined as $\frac{1}{1 + e^{6 - n}}$ where $n$ is \texttt{move\_number}. This is a sigmoid that increases from 0 to 1 approximately around the point at which players leave memorised chess territory. This turning point was found empirically through correlation with the target feature to be around move six.
    \end{itemize}
    
    For training a convolutional neural network model, a feature called \texttt{pieces} representing the state of the chess board was included. This feature was a 3-dimensional array of booleans of size (12, 8, 8) representing the presence of the 12 possible types of pieces (pawns, knights, bishops, rooks, queens, and kings in both colours) on the 8 by 8 chessboard.
    
    \subsubsection{Modelling and results}
    
    The dataset was split 80\%/10\%/10\% into training, validation, and test
    sets. As a baseline, a dummy regressor predicting the mean move time
    achieved an MSE (mean squared error) of 73.33 on the validation set.
    
    A linear regression model trained on the original features achieved a
    validation MSE of 56.81. The training data was then cleaned of
    outliers using the IQR (interquartile range) method, and the two engineered features added, bringing the validation MSE to 62.69. Although this is numerically higher than the unfiltered model, the outlier removal produced a
    healthier distribution of predicted move times. Before, there were a notable number of negative predicted move times, which was much improved after outlier removal. 
    
    This final linear regression model achieved a test set MSE of 64.40, corresponding to an RMSE (root mean squared error) of approximately 8.0 seconds. The training of this linear regression model can be seen in \texttt{/EngineMoveTimeModel/src/main/python/Linear regression model for poster fair (contains was\_capture).ipynb}.
    
    We also trained models with CNNs (convolutional neural networks) making use of the board state as an additional feature. The best performing one of these models was trained in \texttt{/EngineMoveTimeModel/src/main/python/Keras models using pieces attempt 3 even bigger model with AdamW weight decay.ipynb}. In this model the state of the board, a (12, 8, 8) boolean array, was given to a CNN with 3 hidden layers. The number of filters in the layers increase from 64 to 128 to 512. The first two layers use 3x3 kernels with ReLu (rectified linear unit) activation functions, a standard idea ever since the ``VGG'' CNNs \citep{simonyan2015deepconvolutionalnetworkslargescale}. Unlike VGG, we don't use any max-pooling layers because our ``image'' (the chessboard) is already low resolution (8x8 instead of 224x224). Still, we do get spatial pooling as we don't apply any padding before each filter. The final layer uses 4x4 kernels instead of 3x3 so that each filter gives a single output as opposed to a 2x2 output, reducing dimensionality before the dense layers. These 512 outputs from the CNN were concatenated with the other features and passed through 2 dense layers of 32 neurons each to produce the final output. This overall model had 1,147,617 parameters and took over 10 hours to complete 14 epochs of training (TODO ADD HARDWARE CONTEXT). The model achieved a best validation MSE of 51.77 (RMSE $\approx$ 7.2 seconds).
    
    It was surprising that the CNN model was only slightly better than a simple linear regression model (an improvement in RMSE of only 0.8 seconds). A much larger improvement was expected given that the CNN model could make use the state of the board. Instead, what we found is that the clock situation is the most important factor when it comes to how long a player takes to make their move. The features that correlate most with the target feature are \texttt{initial\_time}, \texttt{time\_opponent\_took}, \texttt{time\_remaining\_for\_this\_position}, and \texttt{increment}. 
    
    Disappointing was the high loss. Even the best model had a RMSE of 7.2 seconds. However, the task we're trying to model doesn't necessarily have a single correct answer. Given the exact same clock and board situation, even the same player may decide to take different amounts of time to move. This results in a high loss no matter the model.
    
    
    \subsubsection{Implementation}
    
    Given that the CNN model was large and would have to run as its own microservice while performing only slightly better than the linear regression model, we chose to implement the linear regression model. This can be seen in \texttt{/ChessLibrary/.../RealisticMoveTimeModel.kt}.

    \subsection{Fun animations}
    
    We made the chessboard component ourselves (\texttt{/frontend/src/components/ui/ChessBoard.tsx}). The pieces are animated with the help of the Framer Motion animation library. The two animation options we have are ``normal'' and ``fun''. 
    
    The normal animation option is based on the animations seen on most chess platforms. Piece movement is a linear transition, and a captured piece has an opacity fade out.
    
    The fun animation option adds a rotational wiggle to piece movement, and makes capturing fling the captured piece off the board. Neither \textit{Lichess.org} or \textit{Chess.com} offer such an animation option. At most, \textit{Chess.com} offers an option called ``Arcade'' that adds a blue trail to movement and a red flash to capturing; the pieces themselves don't move any differently.
    
    \subsection{User authentication flow}
    
    We decided to only allow authentication via TOTPs (time-based one-time passwords).
    This avoids having to store users' password hashes, reducing our liability with regard to users' personal information.
    When creating an account, a user is guided through our registration flow: first they pick a username, then they add the TOTP secret we provide to their authenticator app of choice (e.g.\ Google Authenticator, Microsoft Authenticator), and finally they confirm the setup by entering a generated code.
